# Skill: Code Review

## Before Reading Any Code

Size the diff first:
```bash
git diff <base>...<head> --stat
```
- < 10 files / < 500 lines → read all diffs in parallel
- 10–30 files → read one module at a time
- 30+ files or 2000+ lines → read one file at a time: `git diff <base>...<head> -- <path>`

Load `.ai/context/CODING-STANDARDS.md` and `.ai/context/AGENT-GUIDELINES.md` §1 before proceeding.

## Checklist

Run every item from `AGENT-GUIDELINES.md §1` — Correctness, Data Safety, Architectural Rules, Code Quality, Testing.

If the diff includes `.ai/context/*.md` or `.ai/memory/learnings.json` (generated by `/learn`), also run the **Documentation Changes** checklist from `AGENT-GUIDELINES.md §1`.

## Severity Scale

| Severity | Criteria | Merge Gate |
|---|---|---|
| **Critical** | Security vulnerability, PII leak, data loss, broken invariant | Blocks merge |
| **High** | Logic error, missing error handling, broken arch rule | Blocks merge |
| **Medium** | Missing tests for critical paths, performance issue | Should fix |
| **Low** | Better naming, minor refactor | Improvement opportunity |
| **Nit** | Style not enforced by linter | Optional |

## Output Format

```
## Code Review: [branch / PR title]
Files reviewed: N  |  Lines: +X / -Y

### Summary
[1–2 sentences: what the change does and overall assessment]

### Findings
#### Critical / High / Medium / Low / Nits
- **[ClassName.java:line]** [description + suggested fix]

### Documentation Changes (if any)
[Apply Documentation Changes checklist — separate verdict]

### Positive Notes
[Call out anything well done]

### Verdict
APPROVED | CHANGES REQUESTED | BLOCKED
[If not approved: what must change before re-review]
```

## Verdict Rules
- **APPROVED** — zero Critical, zero High. Tests adequate.
- **CHANGES REQUESTED** — High findings or inadequate tests.
- **BLOCKED** — Critical findings (security, data loss, invariant broken).
